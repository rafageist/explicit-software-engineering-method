# 2. From Software to Software Product

Software and software products are not equivalent.

Software consists of executable code, configurations, and data that produce behavior.
A software product is the result of engineering: software whose behavior, constraints, and purpose can be explained, validated, and justified.

The Explicit Software Engineering Method is concerned with the transformation from software to software product.

---

## 2.1 Software Is Output; a Product Is an Outcome

Software can exist without engineering intent.
It may function, pass tests, or satisfy immediate needs, yet remain opaque with respect to:

- why it exists in its current form
- which decisions shaped it
- which assumptions it relies on
- which trade-offs were accepted
- how its correctness or fitness was established

A software product, by contrast, is an outcome whose properties are intentional and explainable.

The distinction is not about size, polish, or commercial packaging.
It is about **engineering accountability**.

---

## 2.2 Engineering Makes the Difference

Engineering introduces structure between problem and solution.

Within this method, software becomes a product only when:

- intent is declared
- decisions are explicit
- assumptions are identified
- trade-offs are acknowledged
- artifacts are traceable
- validation relates directly to intent

Absent these elements, software may function but cannot be said to be engineered.

---

## 2.3 Products Are Diagnosable; Code Alone Is Not

A defining property of an engineered product is diagnosability.

When a software product fails, it must be possible to explain the failure in terms of:

- invalid or incomplete intent
- incorrect decisions
- false assumptions
- missing or insufficient validation
- accepted but underestimated trade-offs

If failure can only be explained by retrospective narrative or individual recollection, the result was software, not a software product.

---

## 2.4 Process Does Not Create Products by Itself

Processes coordinate activities.
They do not guarantee that engineering reasoning is preserved.

A team may follow a well-defined process and still produce software that:

- lacks traceable intent
- embeds undocumented decisions
- relies on implicit assumptions
- cannot be analyzed beyond surface defects

The method does not depend on a specific process.
It defines the conditions under which process execution results in an engineered product.

---

## 2.5 The Role of Explicitness

Explicitness is the mechanism by which software is elevated to a product.

By requiring engineering reasoning to be represented as explicit artifacts and relationships, the method ensures that:

- software outcomes are intentional
- quality is contextual and defensible
- failures are explainable
- learning is cumulative rather than anecdotal

The Explicit Software Engineering Method exists to make this transformation observable, enforceable, and repeatable.

---

## 2.6 Summary

- Software can exist without engineering; products cannot.
- A software product is defined by explicit reasoning, not by delivery mechanics.
- Processes may produce software; the method produces products.
- Engineering becomes real only when it leaves evidence.

The method provides the minimal structure required for software to qualify as an engineered product rather than incidental functionality.
